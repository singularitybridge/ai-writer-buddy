AI Writer Buddy

Hebrew RTL Book Writing Application with AI Assistant

Next.js Hebrew RTL AI Assistant No Build Process fal.ai Integration

Executive Summary

Project Vision

A Hebrew-first book writing platform with integrated AI assistance for content creation, editing, and cover generation. Built without a build process for maximum simplicity and developer experience.

Technical Approach

Shoelace + Alpine.js architecture with Tailwind via CDN. All dependencies loaded from CDN, no npm build step required. Data stored in lowdb for simplicity.

Key Innovation

AI-generated book covers using fal.ai's Flux model, real-time AI writing assistance with contextual chat interface, full RTL support for Hebrew content.

Success Criteria

Authors can create, organize, and write books entirely in Hebrew with AI help. Cover generation takes <5 seconds. Chat responses feel natural and contextual.

Requirements & User Stories

US-01

Book Discovery

As an author, I want to view all my books in a grid layout so that I can quickly find and access my writing projects.

Acceptance:
  • Books display with cover, title, and subtitle
  • Grid is responsive (1-3 columns based on screen size)
  • Clicking a book navigates to book detail page
  • Hebrew text displays correctly RTL
US-02

Book Editing with AI

As an author, I want to write book content with an AI assistant sidebar so that I can get real-time help with writing, editing, and ideas.

Acceptance:
  • Two-column layout: content (2/3) + chat (1/3)
  • Chat shows AI avatar and name
  • Messages styled with bubbles (user/AI different)
  • Chat persists per book context
  • Input area supports Hebrew RTL
US-03

Chapter & Page Navigation

As an author, I want to navigate between chapters and pages easily so that I can organize my book structure efficiently.

Acceptance:
  • Left sidebar shows chapter/page tree
  • Clicking navigates without full page reload
  • Active page highlighted in navigation
  • Supports text pages and image pages
US-04

AI Cover Generation

As an author, I want to generate book covers using AI so that I can have professional covers without design skills.

Acceptance:
  • Trigger cover generation from book metadata
  • Uses fal.ai Flux model via API
  • Shows loading state during generation
  • Cover updates automatically when ready
  • Supports regeneration if unsatisfied

Database Indexes & Relationships

  • Books: Primary entity, no foreign keys
  • Chapters: bookId → Books (many-to-one)
  • Pages: chapterId → Chapters (many-to-one)
  • ChatMessages: bookId → Books (many-to-one, scoped context)
  • Ordering: Use order field for chapter/page sequence

API Specifications

Cover Generation API (fal.ai)

# Endpoint: api/cover.js
POST /api/cover
→ Request Body:
{
  "bookId": "uuid-1",
  "prompt": "A romantic novel cover with mountains at sunset,
             watercolor style, soft colors, Hebrew title placeholder"
}
→ Response (200 OK):
{
  "success": true,
  "coverUrl": "/public/covers/uuid-1.png",
  "generatedAt": "2025-12-06T10:35:00Z"
}
→ Error Response (500):
{
  "success": false,
  "error": "fal.ai API error: rate limit exceeded"
}

Infrastructure & Services

Required External Services

fal.ai (Cover Generation)

Model: flux/dev or flux/schnell
Cost: ~$0.02-0.05 per image
Setup: API key from fal.ai dashboard
Rate Limits: Check tier (typically 100/min free)

OpenAI (Chat Assistant)

Model: gpt-4o-mini (cost-effective)
Cost: ~$0.15/1M tokens input
Setup: API key from platform.openai.com
Context: Max 128k tokens (plenty for books)

lowdb (Database)

Type: JSON file-based database
Cost: Free, local storage
Setup: npm install lowdb (ESM import)
Limits: Good for <100 books, then migrate

Google Fonts

Font: Rubik or Alef (Hebrew + Latin)
Cost: Free
Setup: CDN link in HTML head
Weights: 300, 400, 500, 600, 700

Key Considerations & Risks

⚠️ No Build Process Limitations

Since we're using pure HTML/CSS/JS with CDN dependencies, be aware:

  • • No TypeScript - rely on JSDoc comments for type hints
  • • No module bundling - careful with script load order
  • • CDN failures can break the app - consider fallback CDNs
  • • Limited code splitting - may impact initial load time

🌍 RTL Hebrew Challenges

RTL support requires constant vigilance:

  • • Test every new component in RTL mode
  • • Some Shoelace components may not support RTL out-of-box
  • • Mixed Hebrew/English content can cause alignment issues
  • • Emoji and icons may need special positioning in RTL

💰 API Cost Management

Monitor usage to avoid unexpected costs:

  • • fal.ai: $0.02-0.05 per cover (rate limit: ~100/min free tier)
  • • OpenAI: ~$0.15/1M input tokens (gpt-4o-mini)
  • • Consider caching AI responses to reduce API calls
  • • Implement rate limiting on cover generation button

📊 lowdb Scalability

JSON file-based database has limits:

  • • Works well for <100 books with ~20 chapters each
  • • Beyond that, consider migrating to PostgreSQL or MongoDB
  • • Concurrent writes can cause data loss - implement locking
  • • No built-in search - will need to implement manually

🔐 Security Considerations

API keys and data protection:

  • • Never expose API keys in frontend code
  • • All API calls must go through backend endpoints (api/)
  • • Validate and sanitize all user input (book titles, content)
  • • Consider adding user authentication in future
